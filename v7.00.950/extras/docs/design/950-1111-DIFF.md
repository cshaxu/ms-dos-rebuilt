# 950 → 1111 差异规模与源码组织

结论：建议 v7.10.1111 使用从 v7.00.950 初始化的完整独立源码树。此次仅调查、提出方案，尚未复制或创建该源码树。

输入为用户指定 O:/assets/w9xbd 的 Windows 95 和 Dell OSR2 启动软盘，哈希见 w9xbd-version-survey.json。现有 950 两个可执行产物与新 950 盘一致；MSDOS.SYS 单独按目标配置处理。

这些百分比只是保守的精确字节锚点覆盖，**不是源码恢复率，也不是功能差异率**。先按容器组件对应，再用旧区唯一的 32 字节锚点做保持顺序的位移对齐并延长相同段，每段重新 memcmp；不是从文件偏移零开始硬比。地址、位移或数据引用变化也会打断相同字节段。相同文件自检得到 100%。

BIOS 消息尾标识、资源长度及 4168 字节保留区给出内核起点；950 已验收的生成器/链接产物提供参考边界。OSR2 的 logo 在新位置完整 65384 字节一致，界定内核加段落对齐区的上界。尾部配置程序从各自 MZ header 长度确定。COMMAND 的资源区和装载体也由 MZ header 确定。完整匹配段坐标见 [机器证据](../etc/950-1111-diff.json)。

整文件粗略锚点覆盖为 IO.SYS 61.40%、COMMAND.COM 73.26%，但 IO 包含完全相同的 65KB logo，因此不采用这些整文件数值判断恢复工作量。更有用的结论是：COMMAND 资源大部分复用，驻留消息资源全同；BIOS、内核、配置程序及加载器均须实质核查。配置程序缩小 19064 字节，不能先假定沿用原完整链接布局。

## 为什么不用 overlay

6.21 的覆盖层适合少量且局部的差异。本次已有多个组件尺寸和容器边界变化，而非单个补丁点。依赖上一版本目录的构建 overlay 会把头文件、消息资源、链接顺序和生成工具的版本选择隐含在覆盖规则中，增加以后独立复现与验收的负担。

完整树的初始化仍直接复用 950 代码和原版工具方案，绝不从零重写，也不为同一功能保留 950/1111 两条实现。Git 可以表达相同文件与真实差异；物理目录的复制不等于重新实现。

实施顺序：冻结当前 950 源码及工具清单 → 新目录落地完整 Microsoft 风格树（不复制 build、旧日志、目标和已发布 assets）→ 冻结 1111 三文件目标 → 建立二进制块到符号/文件的差异映射和依赖图 → 只改有证据的文件。每个文件记录与 950 相同或修改；按拓扑顺序处理，真实循环按已获授权的整体单元处理。暂不承诺具体修改文件数，尚未完成函数和文件映射。

构建入口 v7.10.1111/extras/build.cmd，输出 extras/assets；运行时不读取 v7.00.950 的源码目录。外部历史编译器仍采用明确固定的工具依赖，不伪装成目录自带工具。保持 CMD/BAT/C、原版 NMAKE/MASM/C/LINK 风格，编译指令不变时不重编，实际布局变动则验证受影响产物。

本轮核心源码修改 0 个、新增源码审计 0 个；新增 C 比较工具 1 个。没有重编 DOS。
