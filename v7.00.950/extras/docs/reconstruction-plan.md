# MS-DOS 7.0a 三核心源码复建执行计划

## 1. 最终目标和项目边界

以 `O:/repos.hobby/ms-dos-rebuilt/v7.0a` 为项目根，使用经逐字节验证的 6.22 源码作为起始基线，复建本机 Windows 95 A 启动镜像中的 IO.SYS 和 COMMAND.COM 及其构建所需源码、头文件、消息和资源，并按镜像内容生成 MSDOS.SYS。三个最终产物必须分别与镜像提取文件全长逐字节一致。源码组织、汇编格式、注释、命名、过程参数和寄存器约定尽可能遵循微软 DOS 6 源码风格；有证据时才修改或引入源码。

项目根保留完整源码树，而非 6.22 那样的差异覆盖层。项目额外的规则、计划、工具、证据、目标提取文件及构建生成物都放 `extras/`；`extras/build/` 和目标二进制由 `.gitignore` 排除。原镜像及 6.22、6.20、6.0、5.0、DOS 4 和 OpenNT 参考均不改动。禁止使用 Computer Use；禁止向 `D:/temp` 和 `D:/tempu` 写入，临时文件和构建结果归项目 `extras/build/`。当前验收不要求 SoftPC 或虚拟机启动测试。

目标 MSDOS.SYS 是本镜像中的六字节配置文本 `;SYS`、CR、LF，不等于 DOS 6.22 的独立内核；7.0a 实模式内核及引导相关代码应依据目标布局定位，不能照搬三文件的旧分工。目标 IO.SYS、COMMAND.COM 以 MZ 头开始；结构、可执行区与任何打包格式须以证据确认，不能只凭扩展名或头字段推断。

## 3. MTSP 里程碑与任务

### M0：目标与完整源码基线

已完成素材提取、镜像和目标登记、完整源码落地、220 文件台账及基线构建。目标文件按需重提取，不纳入提交。后续若发现来源或清单缺漏，登记更正并保留原证据，不把 M0 构建误记为 7.0a 验收。

### M1 / T1：7.0a 布局与源码映射

**S1（进行中）— 解析目标结构。** 分析文件头、启动入口、加载边界、代码数据区、实际链接/打包格式及资源；使用反汇编、偏移锚点与 6.22 MAP/LST 对照，不把 MZ 头声明自动视作真实启动路径，不把偶然 `MZ` 字节认作嵌套文件。分别登记直接证据、基于参考的推断和未知。输出可重复的区间映射，以及对第一个待处理文件的明确证据。

**S2 — 依赖和构建闭包。** 映射 7.0a 实模式内核、BIOS、COMMAND、消息与共享头文件的可证实依赖；记录所需新模块、数据、生成器和工具版本/哈希。对未知布局或缺少来源逐项记录，不将其假定为 DOS 6.22 一致。定出源码文件队列、模块依赖及阶段构建方案。

验收：输入及偏移可重复核验，组件边界和尚未识别区域明确；首个处理文件及其证据、依赖和验证方式明确。

### M2 / T2：按固定文件顺序复建

按照已核实的依赖关系对文件拓扑排序：只有直接依赖均已处理并验证后，才能开始处理依赖它的文件。源文件一旦发现尚未完成的依赖，立即停止修改，登记依赖并先处理满足条件的前置文件；不得将历史列表编号当作执行顺序。先完成依赖图，区分条件编译、声明依赖、实际构建依赖和链接布局依赖；未知、歧义和循环不得假定为已解决。循环必须先核实并消除虚假边；用户已允许将核实后的真实循环作为一个处理单元，单元外前置依赖必须先完成，单元内仍按文件记录顺序、修改及验证。宏模板中仅在调用时产生的外部引用须记录并在实际调用方建立依赖，不能当作已经验证。每个文件保留目标偏移、对应功能、源码变化、可重复验证及未决项，源码保持微软历史风格。静态初筛不是完整依赖图或合格证明。

自动批量分类只用于可证明的相同文件或相同代码段，并以目标版本二进制及受控参考为依据；保留 NT/BOP 清理要求，但仅在真实引入相关代码且有证据时处理，不能把合法 DOS 代码误判。无法确定与目标是否一致的文件保持待核验。新发现的必要源码按新增编号追加到台账，不重排原 220 个编号；目录结构仍遵循微软惯例。对结构无法验证、推断命名或注释注明证据等级，不伪造原始来源。

验收：每个纳入的文件或必要依赖均有明确处置和证据，源码符合原微软风格；直接影响范围有汇编、链接或目标二进制对照验证。因代码布局或依赖变化无法判断时记录为待验证，不提前宣称完成。

### M3 / T3：组件集成与构建

依据目标布局恢复 IO.SYS 的加载、BIOS、内核、资源及必要的文件封装；恢复 COMMAND.COM 相关代码、资源、链接和封装；根据目标六字节内容生成 MSDOS.SYS。固定工具和依赖版本、工具哈希、编译选项、链接顺序、消息生成流程及输入哈希，保留可重复构建脚本。中间验证可以分组件进行，但最终构建必须从 v7.0a 完整源码与已登记工具产生文件，不能直接复制目标执行文件、嵌入目标整体或用不可审计二进制补丁冒充源码。

验收：三个文件可在新的隔离构建目录生成；依赖、构建输入和未解决差异完整可追溯。需借助 6.22 构建脚本时必须明确它是临时基线，最终构建不能把 6.22 目标文件当产物。

### M4 / T4：独立验收与交付

重新校验目标镜像与文件哈希，检查源码台账、固定工具、输入闭包及当前构建来源；在干净的项目内构建目录运行完整构建。对 IO.SYS、MSDOS.SYS、COMMAND.COM 各自做全文件字节比较、长度和 SHA-256 核验，输出比较结果及第一个差异（如有）。验证构建前后源码和参考输入未变，检查忽略规则及项目结构，记录未决来源与无法证实的源码文字。

完成条件：三个产物全部逐字节一致；源码和实际依赖均已登记，构建可复现，差异及待验证项为零或已明确不影响目标且说明；逐文件计数可由台账复算。源码文本与原微软源码的逐字一致不作为已证明事实。任何单项失败都不能称项目完成。

## 4. 进度口径

每次汇报同时列出：台账总文件数、已处理数（修改/未修改）、当前文件序号和路径、待处理数、新增文件数，以及三个目标的最新构建结果。`unchanged_from_v6.22` 只表示当前字节相同，不等于已证实是 7.0a 原始源码；未处理文件不得计入已验证。台账总数随必要新文件登记而变化，原编号不重排。项目状态以 [CURRENT.md](states/CURRENT.md) 为准。
