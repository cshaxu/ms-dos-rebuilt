# Rebuilding and comparing the three system files

Run commands from the project root, `O:\repos.hobby\ms-dos-archaeology\v5.0`.
The source inputs are `bios/` for IO.SYS, `dos/` for MSDOS.SYS,
and `cmd/command/`, `inc/`, and `messages/` for COMMAND.COM. The kernel uses
the top-level `inc/` files listed in `extras/tools/kernel_includes.txt`. Earlier
investigation material is preserved under `extras/research/dos/`.

BIOS class 1 and class 3 messages are generated by NOSRVBLD from
`bios/msbio.skl` and the recorded message inputs. The `bios/msbio.cl1`
and `bios/msbio.cl3` files are earlier recovered references, not inputs to
the current local-source build.

BIOS and kernel share `messages/usa-ms-dos.msg`; each generates its index
in its own build stage.
COMMAND uses `messages/usa-ms.msg` and generates its index in its own stage. The variants differ in a version message and an inferred optional POWER
message and are retained separately to preserve the component resources.

BIOS retains 21 same-name private headers: 15 differ from the common files
only under the narrow notice/blank-line/EOF comparison, while six have other
differences. `python extras/tools/audit_bios_include_variants.py` records their hashes
and dispositions; the notices and configuration branches are preserved.

`python extras/tools/preflight_source_build.py` checks the pinned external historical
tools, isolated launcher, and retained comparison inputs without launching a
build. `python extras/tools/audit_style_cleanup.py` compares the current inputs with the
recorded integrated BIOS inputs and latest verified kernel and COMMAND source
snapshots. Both are read-only checks; neither performs a build.

External paths may be set with `DOS5_TOOLS16_ROOT` (directory containing MASM,
NOSRVBLD, BUILDIDX, BUILDMSG and STRIPZ), `DOS5_DOS6_ROOT` (DOS 6 tree containing
`c6ers/tools6/bin`), and `DOS5_DOSBOX_PATH` (DOSBox executable). Unset values
use the existing local defaults. Preflight checks the expected tool hashes.
The isolated launcher remains `extras/build/isolated-tool-runner.exe` and its hash is
checked; its source is `extras/tools/isolated_tool_runner.c`. The baseline remains
`O:\DOS`. Tool redistribution and relocation are not established by this build.

`python extras/tools/audit_host_build_dependencies.py` statically inventories PE imports
of the current MASM, DOSBox, isolated runner and Python, recursively including
DLLs beside each executable. The observed DOSBox installation includes SDL.dll
and SDL_net.dll; their current hashes are recorded in
`evidence/host-build-dependencies-current.json`, but were not captured during
earlier builds and are not preflight pins. The integrated build now records
them before and after building and rejects a change; this does not establish
which DLLs Windows actually loaded or exclude changes between observations.
Imports resolved elsewhere, dynamic loads, Python modules and operating-system dependencies remain outside this
static inventory. It invokes objdump, not the build tools.
When the pinned launcher is missing, `python extras/tools/build_isolated_runner.py`
reproduces it from source using GCC 16.1.0 with a fixed PE timestamp. The script
checks the source and output hashes and will not overwrite an existing file or
execute the result. Other toolchains must produce the same pinned hash. See
`evidence/m6-isolated-launcher-reproducible-audit.json`.

For diagnostic source builds, `python extras/tools/build_debug_kernel.py --report <new-filename.json>`
assembles and links a separate DEBUG kernel with `dos/msdos-debug.lnk`. The
diagnostic build is not a target-identical or runtime-validated DOS release.
Its DOSPRINT module is retained from DOS 6 and statically targets COM1; DOS 4
used INT 29h, and the DOS 5 DEBUG output method is unverified. Build inputs and
comparison limits are recorded in `evidence/m6-debug-source-closure-audit.json`.

The integrated build entry point is `python extras/tools/build_integrated_source.py`.
The integrated build checks the linked SYSINITVAR-to-START_ARENA layout
against the 6Ah-byte invariant formerly asserted in msconst.asm. Direct
component builds do not perform this integrated check.
The integrated entry point runs the pinned prerequisite hash checks before
creating a build stage or starting tools, and records the results in its report.
The component scripts invoked directly do not provide this integrated check;
a file could also change between checking and use.
The `dos/makefile` and `cmd/command/makefile` all targets invoke this same
three-file recipe; the recipe has been run from both directories, though NMAKE
itself was not available to test.
It runs the MSLOAD, BIOS, kernel and COMMAND recipes in new directories under
`extras/build/`, then checks the three resulting files byte for byte against the
three hash-pinned retained files in `O:\DOS` and verifies their sizes and hashes.
The build reads this baseline before and after compilation; it does not modify it. The recipes
use the historical tool paths checked by preflight and the isolated desktop
launcher; the owner's permanent Computer Use prohibition still applies. Any
applicable execution approval or rejection must be respected. A preflight
success does not authorize execution.

For recorded build inputs, `python extras/tools/audit_build_input_manifest.py --stage
<integrated-stage> --report <new-filename.json>` checks staged source, includes,
resource hashes and the loader/BIOS BUILDIDX message transformation. The
report does not establish operating-system dependency closure or distribution
rights.

Its component assembly and verification limits are documented in
